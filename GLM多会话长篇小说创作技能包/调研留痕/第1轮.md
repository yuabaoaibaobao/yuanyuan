# 第 1 轮 · 平台机制轮（P2）

## 检索目标
确认 GLM / 智谱清言项目、自定义指令、长期记忆、会话隔离、项目文件区、字数限制、指令与记忆优先级、多会话协作在真实平台上可落地，不写出平台做不到的指令。

## 检索式 / 资料域清单
1. 智谱清言 GLM 项目 自定义指令 长期记忆 区别 字数限制
2. GLM 智谱清言 项目文件 会话隔离 多会话协作
3. 智谱清言 项目 自定义指令 记忆 优先级 冲突

资料域：智谱开放文档记忆机制、清言 App 需求 Issue（跨会话记忆缺失）、GLM 多会话管理实测（KV Cache 隔离）、清言进阶技巧（任务拆分与验收）、模型输出字数限制实测。

## 关键发现（逐条编号）
- **1.1 会话隔离真实**：GLM Web 多会话底层为每会话分配独立 KV Cache，A 会话与 B 会话完全不互相污染；跨会话记忆缺失（清言 App Issue #152 明确列为能力空缺）。→ 总控 Prompt §1.5/§13 的“上下文不互通、文件互通”在平台上成立，必须靠项目文件区传状态。
- **1.2 记忆分层与冲突风险**：开放文档记忆机制指出组织级 > 项目级 > 用户级，冲突时 Agent 可能随机选择，过大记忆文件占用上下文、降低遵循度、增加冲突概率。→ 支持 §1.4 优先级铁律（01 > 02 > 会话规范）与 2000 字上限（拆分 + 索引，不塞大文件）。
- **1.3 输出字数限制**：大模型单次输出约 1000 字左右，超量需分段输出再合并。→ 正文必须按章/场景分段生成 + 交接包合并，不可一轮写整卷。
- **1.4 高质量对话靠拆分与验收**：清言进阶技巧总结为“明确任务、提供可核验材料、拆分阶段、设置验收标准”，长文先复述目标与未知项、再生成结构、逐节写作、最后事实/逻辑/格式检查。→ 支持 §4 状态机 + §8.6 单夹自检 + §14.9 一致性检查表。
- **1.5 长上下文≠有效上下文**：清言标称 32K–1M tokens，但有效可用上下文小于标称（lost-in-the-middle），关键信息需置于首尾。→ 不可把“塞全文”作为长篇方案，必须滚动摘要 + 文件回读（§14.8）。
- **1.6 多轮记忆调用≠跨会话记忆**：单会话内可主动调用历史信息，但新会话需重新交代背景。→ 每个会话指令必须内嵌读取清单（§13.3），禁止“参考前文”。

## 吸收点（写进包里哪份文件的哪一节）
- 1.1 → `01_自定义指令.md` 唯一状态通道条；各 `作者X/会话指令.md` 开篇“上下文不互通”声明（§8.4）。
- 1.2 → `01` 优先级声明 + `02` 自限条（§6.2-2、§7.2-6）；`导入检查单.md`（外置）优先级勾选表。
- 1.3 → `作者四/规范/正文生成规范.md` 分段生成量（按体量三档换算）。
- 1.4 → `作者X/自检清单.md` 三表；`作者六` 审校规范。
- 1.5 → `作者四/规范/滚动摘要规范.md`（§14.8）；`01` 开工读取纪律。
- 1.6 → `作者X/输入输出契约.md` 读取清单列到具体文件名（§13.3）。

## 舍弃点及理由
- 舍弃“靠超长上下文塞全文写百万字”：有效上下文不足，且平台输出限制不支持；改为文件外化状态（第 2 轮进一步修正）。
- 舍弃“记忆文件写流程”：记忆过大降低遵循度且与指令冲突；02 只写人格（§7.3）。

## 存疑点
- 自定义指令/长期记忆 2000 字上限在公开文档未直接查到原文数字，以总控 Prompt §1.2/§1.3 与用户 P1-6 确认为准；包内按 2000 字上限设计，实测字数在 README 记录。
- 项目文件区具体容量与版本管理 UI 未查到，包内以“带版本号 + 广播”协议兜底，不依赖平台版本 UI。

## 对下一轮方向的修正说明
- **因 1.1/1.5 发现**（会话隔离 + 有效上下文不足），第 2 轮不再调研“如何塞更多上下文”，转而调研“如何把状态外化为可检查文件”（设定圣经、连续性编辑、Story Skills compiler 思想）。
- **因 1.2 发现**（记忆过大降低遵循度），第 2 轮重点调研“规范如何拆分 + 索引 + 模板填空”，避免大文件堆叠。
